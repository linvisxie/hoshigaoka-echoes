## 三、交付内容

### 3.1 数据层（唯一数据源，B6）

| 文件 | 内容 |
|---|---|
| `data/equipment.json` | 3 个装备固定模板（1-2 优秀武器 / 1-6 优秀治疗饰品 / 1-9 稀有通用饰品） |
| `data/equipment_affixes.json` | 3 个固定词条（武器攻速 5% / 饰品生命 60 / 饰品冷却 5%） |
| `data/upgrade_costs.json` | 新增 `equipment` 段：+0→+10 十档成本、上限 10、成功率 100%、重置返还率 80% |

**规格纪律落实**：

- **L1597（LOCKED）不随机**：全部模板与词条均为固定值；实现中**不存在任何随机数调用**。
  已用测试证明：同一模板反复实例化 20 次得到**完全相同**的面板（`test_01d`）。
- **L1598 数据契约**：`equipmentId` = 模板 ID，`instanceId` = 背包实例 ID，
  同一模板可持有多件实例（`test_01e`）。
- **表 63 三槽位**：`WEAPON` / `ACCESSORY` / `MEMENTO`（`test_01b`）。
- **表 64 四档品质**：词条数量按品质结构校验（优秀 1 副 / 稀有 1～2 副）（`test_01c`）。
- **L1611 原子性**：每次处理按唯一 `instanceId` 提交。

### 3.2 领域层

| 文件 | 内容 |
|---|---|
| `scripts/domain/economy/equipment_service.gd`（新增） | 模板查询 / 实例化 / 权益兑现 / 装配 / 强化 / 重置 / 分解 / 面板计算 |

**关键设计**：

1. **权益兑现（复用 A0.4）**：`fulfill()` 在**同一内存事务**内「创建实例 + 兑现权益」，
   再统一 commit。若权益兑现失败则**回滚刚写入的实例**，不留孤立实例（`test_05`）。
2. **幂等**：权益不在 pending 中（已兑现）时直接失败，**不复制装备**（`test_04`）。
3. **实例不复制模板数值**：实例只记录「身份 + 强化等级 + 累计投入」，
   面板一律从模板/词条读取并计算，避免同一件装备在两处各存一份（B6 SSOT）。
4. **分解的领域层闸门**：L1611 要求「分解强化装备必须先选择『重置后分解』或
   『直接分解且放弃投入』，UI 明示差别」——本实现把这条**落成领域层可验证的闸门**：
   未确认时 `dismantle()` 直接拒绝（`test_09b`），而不是只靠 UI 自觉。
5. **「不可凭空返还」**：重置后**清零累计投入记录**，因此重复重置第二次返还 0（`test_08b`）。

### 3.3 数据校验（DataRegistry 新增）

`_validate_equipment_references()` 在加载期校验：

- 模板的 `affixes[]` 必须存在于 `equipment_affixes.json`（L1598）；
- 模板的 `slot` 必须是表 63 三槽位之一；
- **`stage_rewards.json` 的 `equipmentId` 必须存在于 `equipment.json`**——
  否则首通权益兑现时会因「模板不存在」而失败，即**不可逆的奖励损失**；
- 装备强化成本只能引用 `currencies.json` 里存在的资源。

## 五、经济自洽性（对照表 71）

表 71（L1689）：装备零件 15～24，「允许进行早期强化，但不要求刷装」。

| 项 | 值 | 校验 |
|---|---|---|
| 全章首通总给装备零件 | 20（10 关 × 2） | 落在 15～24 区间内 |
| 单件装备强化满（+0→+10）累计零件 | **15** | 20 − 15 = **5** 余量 → 恰好「够强化满一件且有富余」 |
| 单件强化满累计学园币 | 1450 | 占全章 5200 的 **27.9%**，与表 71「少量装备强化」一致 |

> 该数值关系已固化为回归断言（`test_11_enhancement_budget_is_consistent_with_table_71`），
> 后续调表若破坏「单件满强化 = 全章给量 − 5」这一关系会立刻失败。
